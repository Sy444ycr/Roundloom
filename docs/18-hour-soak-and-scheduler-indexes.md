# 一小时负载与历史调度查询修复

## 基线发现

原计划运行一小时。在约 15 分钟的基线阶段发现任务延迟随历史量增长：最近任务 p95 从约 0.8 秒升至约 1.4 秒。调度器每 20 ms 读取、解析全部历史 Run，再筛选活跃运行；3265 条记录时一次测量的平均扫描耗时约 24 ms，已经超过调度间隔。

基线被主动中止以修复这个可扩展性问题，没有达到一小时，也没有记为通过。保留的 [中止记录](verification/hour-soak-interrupted-baseline-2026-11-13.json) 和本地 SQLite 快照用于追溯。

## 修复

- 活跃运行使用按状态过滤的 SQLite 部分索引，会话执行锁只查询对应 sessionId。
- 任务关联运行、任务关联同伴请求、来源 Run 的同伴请求使用 JSON 字段表达式索引。
- 同伴超时检查只扫描已到期的 pending 请求；派发表只检索 pending 项。
- 关闭、恢复和取消路径复用活跃运行查询，避免历史终态记录进入高频处理。
- 负载脚本的循环检查也改为活跃查询，结束时另做一次完整历史扫描，确认没有漏掉残留运行。

这些是兼容的派生索引，旧数据库打开时通过 CREATE INDEX IF NOT EXISTS 自动补建，不改业务数据格式，schema 仍为 v1。状态更新与事务回滚由 SQLite 同步维护索引。历史查询 API 仍返回完整结果，没有删除历史以换取性能。

在同一份 3328 条运行、0 条活跃运行的快照上，[查询比较](verification/scheduler-query-comparison-2026-11-13.json) 的平均耗时为：全量读取并解析 14.792 ms，索引活跃查询 0.0148 ms。它是特定快照的查询比较，不代表所有场景的整体性能倍数。

新增回归测试使用 10000 条历史运行，验证活跃状态、会话过滤、任务关联、事务回滚、旧数据库补建索引和同伴到期边界。43 项自动化测试通过。

## 一小时复测口径

修复后重新从空数据库开始运行 3600 秒，沿用原有任务分布、到达速率、取消比例、幂等重试和性能阈值，不放宽门槛。中途排空队列后关闭并重新创建 Core 一次，继续使用同一数据库；这不是操作系统进程重启。

```powershell
npm run test:soak -- 3600
```
