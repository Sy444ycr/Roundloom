# 实施工具选型与 M1 计划

日期：2026-11-13｜状态：基于已确认架构形成的实施建议；尚未安装依赖或开始编码

## 1. 收敛方案

| 项目 | 首选方案 | 理由与替代条件 |
| --- | --- | --- |
| 开发语言 | TypeScript，启用严格检查 | 共享 IPC、领域与适配器类型；边界仍需运行时校验 |
| 前端 | React + Vite | 与既有经验及已确认界面架构一致 |
| 桌面构建 | Electron Forge + 官方 Vite 插件 | 集中处理开发、打包和安装产物；Core 单独配置构建入口 |
| 包管理 | npm workspaces + 单锁文件 | 对应现有模块目录，减少额外构建编排；CI 使用锁文件安装 |
| 数据库 | SQLite + WAL | 本地事务存储，Core 统一拥有连接 |
| 驱动 | better-sqlite3，仓储接口隔离 | 同步事务易于表达；首先验证 Electron 原生模块兼容，失败时评估替代驱动 |
| 数据访问 | 参数化 SQL + 显式版本迁移 | 首版不增加 ORM；事务与约束保持可见 |
| 首发环境 | Windows 原生，先验证 x64 构建 | 基于当前工作环境的规划假设，实际系统和架构初始化时核验 |
| 首版分发 | Forge 打包目录用于早期验证；Squirrel.Windows 安装包用于 M1 出口 | 先确认打包路径和运行能力，再验证安装/卸载行为 |

Electron 和进程架构已确认；表内其余技术为本轮收敛建议，不伪记为用户逐项确认。Windows/WSL/macOS/Linux 分别记录验证状态，当前不声称跨平台可用。WSL Agent 需要专用启动、路径和取消语义，后续独立适配，不隐式转换 Windows 路径。

Forge 8 发布记录说明 Vite 插件已稳定，且构建工具对 Node 有版本要求；旧插件页面仍可能反映早期实验状态，采用新版发布记录作为依据。具体 Electron、Forge、Vite、React 和驱动版本须在初始化时核对兼容范围并锁定，不照抄网页示例版本。[Forge 8 发布说明](https://github.com/electron/forge/releases/tag/v8.0.1)

electron-vite + electron-builder 保留为替代构建链，只有首选链出现明确阻碍时再调整，不同时维护两套打包流程。[electron-vite 分发说明](https://electron-vite.org/guide/distribution)

## 2. 存储设计落地要求

Core 使用参数化查询与短事务。事务内不得等待模型、网络、文件下载或跨进程应答。同步数据库操作仍可能阻塞 Core，需限制单次查询、输出批次和日志读取规模；若实测影响取消响应，再评估存储线程，不能通过关闭可靠性选项掩盖问题。

初始建议启用 foreign_keys、WAL、synchronous=FULL，配置有界 busy timeout。SQLite WAL 的正常读写仍受单写入者约束，数据库放在应用本地数据目录，避免网络文件系统。FULL 的同步行为仍依赖操作系统与存储设备正确实现，不保证抵御硬件损坏。[SQLite WAL](https://www.sqlite.org/wal.html)、[同步配置](https://www3.sqlite.org/pragma.html)

首批数据结构覆盖 rooms、members、connections、sessions、messages、tasks、runs、events、dispatch_intents、peer_requests、artifacts、test_evidence、acceptances、idempotency_records 与 schema_migrations。JSON 用于版本化扩展负载，不替代必要关系约束。

约束至少包括：幂等键作用域唯一、房间事件序号唯一、平台 ID 主键、归属版本校验，以及核心执行锁对共享原生会话唯一生效。事件查询按 roomId/sequence 索引，派发扫描按状态与可执行时间索引。具体表字段在 M1-B 固化并审阅迁移。

文件与数据库不能假装跨介质原子提交：先将产物写入临时文件、校验并移动至受控位置，再提交数据库引用；崩溃遗留孤立文件由恢复扫描识别。数据库记录不存在或缺失的文件不能标为可用。日志文件引用遵循同样原则。

迁移前生成一致性备份，记录 schema 版本和校验结果；恢复需停止写入。不得在活跃 WAL 状态下只复制主数据库文件作为完整备份。应用遇到更高 schema 版本时拒绝写入，不自动降级；卸载默认不清除用户数据，清理需独立操作。

better-sqlite3 是候选驱动，不以系统 Node 下导入成功代替 Electron 测试。原生模块须匹配 Electron ABI，并核对打包解包位置；Forge 提供重建支持，仍需在 Core utility process 实测。[驱动项目](https://github.com/WiseLibs/better-sqlite3)、[Electron 原生模块说明](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules)

## 3. 构建与交付约定

Main、Preload、Renderer、Core 各有构建入口；Main 启动已构建的 Core 文件，不执行 TypeScript 源文件。Renderer 禁止引入 Node 专用包。native 依赖作为运行时依赖保留并按实际需要解包，ASAR 外的可执行资源使用打包后路径定位。

开发命令与打包命令独立。建议统一提供 dev、typecheck、lint、test、package、make；这些只是后续脚本约定，当前并不存在对应可执行命令。纯领域测试与 Electron 原生依赖测试分开，避免不同 ABI 产物相互覆盖。

每个构建记录代码 revision、锁文件摘要、开发 Node、Electron 内置 Node、依赖版本、目标系统与架构。安装产物附版本、校验摘要、已知限制和测试报告。M1 不启用自动更新服务；签名与公开发布在真实交付前单独落实。

Windows 安装包拟采用 Squirrel.Windows；处理安装事件应先于普通业务启动，防止安装/卸载过程中启动 Core。安装包生成不等于签名或发布已完成。[Squirrel.Windows 文档](https://www.electronforge.io/config/makers/squirrel.windows)

## 5. M1 演示与退出条件

固定演示：建群 → 添加两个模拟成员 → 定向讨论 → 显式派单 → 求助并续接 → 提交带版本的模拟产物 → 用户验收。随后演示窗口关闭重开、取消后迟到回复、Core 崩溃与状态未知。模拟测试记录必须醒目标注，不能作为真实测试通过证据。

M1 出口要求：打包版主链路可运行；适用用例有结果与日志；无数据丢失、越权、重复副作用或错误完成标识类阻断缺陷；未实现能力可见；开发和运行说明可复现。TC-24 的真实 Agent 部分留到 M2，M1 只验证打包环境与模拟子进程。
