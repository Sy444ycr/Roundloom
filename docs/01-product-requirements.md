# Roundloom 产品需求说明

> 2026-11-13 更新：首发形态已确定为桌面应用。本文涉及本地 Web 首发的内容为历史候选，桌面进程、通信和生命周期以[桌面架构选型](09-desktop-architecture.md)为当前推荐；其余业务语义继续有效。

版本：v0.1，待评审。产品名已确定为 Roundloom，需求与实施方案仍处于评审阶段。

依据：当前对话中用户明确提出的产品设想与约束。本文描述预期行为，不代表能力已经实现或外部 Agent 已验证兼容。

## 1. 产品目标

Roundloom 是一个以项目群聊为主界面的 Agent 协作工具。用户将真实的不同 Agent 加入同一个项目群，通过点名交流和显式任务分配推进工作；成员可以围绕任务互相提问、分享材料和交接，最终留下代码产物及可核验的测试结果。

协作角色由需求和成员能力决定。用户可以让同一个成员讨论、实现或审查，也可以临时调整分工，不预设固定的规划、开发、测试流水线。项目用于展示 AI 应用工程能力，应能说明请求如何被路由、上下文如何传递、结果如何验证。

## 2. 已确认、建议与待确认事项

### 用户已确认

- 项目名称采用 Roundloom。
- 采用类似 QQ 群聊的交互，用户与 Agent 都作为群成员出现。
- 用户能够点名成员、分配任务；Agent 能够互相交流和协作。
- 接入应开放、可扩展，不限于 Claude Code、Codex 或对话中提到的 dsh；允许同类 Agent 的多个实例。
- 目标包含可运行代码和真实测试结果，作为独立的新项目推进。
- 当前先完成文档工作，暂不进入应用实现。

### 建议的首版范围，尚待评审

先以本地单用户使用为基线：围绕一个明确项目工作目录，完成成员登记、消息路由、任务协作、产物追踪与停止控制。接入采用可替换适配器，并用选定版本的实际测试确认能力。群聊、任务和产物视图先保持简洁。

这一范围用于降低首版复杂度，不是用户已经确认的部署形态。首批接入对象、实际支持数量、优先级、技术栈、工期及模型预算均待确定。对话中的 dsh 暂按前文采用的 DeepSeek Harness 指代，实际产品与版本在首批接入清单中登记。

## 3. 核心对象

| 对象 | 产品含义 |
| --- | --- |
| 项目群 | 聚合成员、消息、任务及项目材料的协作空间。 |
| 成员 | 群内可被寻址的用户或 Agent 实例。显示名称与稳定实例 ID 分离，同类、同名实例仍可区分。 |
| 会话 | 某个 Agent 的持续执行与上下文状态。群聊记录不等于所有成员共享的模型上下文。 |
| 消息 | 一次发言、提问或回复，记录发送者、接收者、关联任务与回复关系。普通消息不自动成为任务。 |
| 任务 | 显式提出的工作请求，包含负责人、目标、验收条件、状态及执行记录。 |
| 产物 | 与任务关联的文件、变更、报告及测试证据，应能定位到具体版本。 |

## 4. 主要用户流程

1. **建群与添加成员。**用户建立项目群，选择已有适配器或自定义连接，填写实例名称并按需关联工作区。界面展示真实连接状态及能力；仅登记配置的成员仍处于未连接状态。
2. **讨论与派发。**用户在群内讨论需求，点名成员请求回复。需要执行时，明确创建任务并指定负责人、目标及验收条件。聊天记录保留，任务以可查看的消息卡呈现。
3. **协作与调整。**执行成员遇到问题时向另一个成员求助，回复关联原任务。用户可以补充约束、调整分工或提出交接；是否继续执行由任务状态和适配器能力共同决定。
4. **查看成果与处理失败。**用户打开产物、变更和测试记录，判断是否满足验收要求。失败、无法验证或被取消的结果应保留原因；重新尝试能够与上一次区分。

例如，用户给一个成员分配“增加 CSV 导出，并处理空值”的任务；该成员请求另一成员确认字段约定，再继续实现。另一成员不因此被永久定义为审查员，后续任务仍可自由分配。

## 5. 功能需求与可观察验收点

### FR-01 动态接入和群成员多实例

支持通过适配器登记、连接和识别 Agent 实例，展示连接状态及已验证能力。兼容矩阵记录适配器、Agent 版本、验证环境与结论，不能用“支持某品牌”替代具体验证。

**验收：**同类两个实例具有不同 ID，能够分别出现在成员列表及点名选项中；连接失败可见原因；未验证的能力明确标注，不能显示为已支持。

### FR-02 群消息、点名路由与引用

群消息可供成员查看，但可读范围与执行触发分开。普通发言、定向提问和任务消息有可辨认类型；明确接收者的消息只触发相应成员，不因出现在群内而唤醒全部 Agent。

**验收：**发送普通消息后可见记录；定向提问的接收实例与用户选择一致，其他成员没有新增执行；回复能回溯原消息。普通问答不会自动增加任务。

### FR-03 显式任务分配

用户通过明确的任务操作指定负责人和工作目标，可补充验收条件。任务展示待处理、执行中、等待、待验收、完成、失败或取消等可理解状态，状态变化须有事件依据。

**验收：**创建任务后，消息卡与任务面板指向同一任务；负责人可由实例 ID 核对；执行失败不显示完成，缺少必要信息时能说明等待什么。

### FR-04 异步同伴求助与交接

支持 Agent 围绕关联任务异步提问，等待回复时可保留进度，回复到达后交还发起成员。主动求助需要接入端具备工具调用或回调等能力；单纯生成“请另一成员处理”的文字不能视作已经派发。求助不会自动改变任务负责人；正式交接使用明确操作，并记录前后负责人、背景和待办事项。

**验收：**一次求助可看到发起者、接收者、任务关联及回复去向；不支持主动调用的成员显示能力限制；交接后负责人和上下文可追踪。

### FR-05 执行事件、流式展示与断线恢复

保留消息、任务状态、协作请求、工具结果及执行尝试的顺序；有流式事件时展示增量输出。群聊客户端重连时补齐平台已持久化的记录。原生 Agent 连接中断后，按适配器能力核对运行状态、恢复订阅或续接会话；无法取得的原生事件标明缺口。需要重新启动时明确记录为新的执行尝试，不因网页重连自动新建会话或重复执行。

**验收：**断开后可见中断状态；恢复时说明是否续接原会话；历史记录仍可查看，同一结果不会因事件重发而产生重复的任务完成记录。

### FR-06 执行控制、等待处理与取消

提供暂停群内新分派和取消指定任务的入口；等待用户输入或许可时，展示原因及待回应内容。暂停新分派与停止已运行进程是不同操作；取消应体现请求中、确认成功、不支持或失败等实际结果。

**验收：**暂停后没有新的自动派发；等待事项可回应；取消结果来自接入端确认，不支持停止时明确提示。既有文件变更和执行记录仍然保留，不暗示取消会自动回滚。

### FR-07 会话与工作区边界

明确展示成员当前关联的会话、可选工作区和允许访问范围。远程或咨询成员可以没有本地工作目录。成员按任务接收必要材料，群内可见内容不必全部注入模型上下文；共享材料与私有会话状态应可区分。

**验收：**同类两个实例的会话标识可区分；向一个实例补充材料不会无提示地改变另一个实例的上下文；新建与续接会话在记录中有明确标识。

### FR-08 产物、版本与真实测试证据

产物关联任务、提交成员及文件或变更版本。测试证据应来自真实执行，保留命令、工作目录或执行环境引用、执行时间、退出状态和必要日志；无法获得的证据标记为未验证。修改之后的版本不能沿用旧版本的通过标识。

**验收：**用户能从任务打开对应产物并定位版本；测试结果可追溯到执行记录；只有文字自述“测试通过”时不显示已验证通过，未运行和运行失败可区分。

## 6. 非功能要求

- **可追溯：**用户能从一次回复或状态变化找到来源；展示成本或耗时时说明数据来源，未知值不猜测。
- **可控：**成员访问范围与任务权限可识别；如需凭证，应通过独立配置管理，不进入公开群消息或共享上下文。
- **可恢复：**超时、重复事件和进程中断有明确反馈；重试保留原尝试，文件冲突应被暴露而非静默覆盖。
- **可用：**主要操作支持键盘，长消息和错误信息可阅读；性能目标在选定真实接入方式后再设定。

## 7. 后续范围与评审重点

远程 Agent、多用户协作、成员间细粒度权限、共享服务部署及适配器分发可作为后续方向，需分别评估身份、连接与隔离机制。本版不承诺一次覆盖所有主流 Agent，也不承诺任意工具接入即具有全部协作能力。

下一轮评审应确定首版使用环境、首批验证对象、哪些能力必须完成，以及失败时怎样降级。通过评审后，再将需求转为接口与验收安排；本文件不附实现代码或自动开工指令。
